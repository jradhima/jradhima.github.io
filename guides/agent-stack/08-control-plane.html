The run control plane

The layer behind "spawn an agent in the cloud": accepting tasks, preparing environments, streaming progress, enforcing budgets, and cleaning up no matter what fails.

In one minute

"Spawn an agent in the cloud" hides a lot of work: accept a task, prepare a workspace, create the sandbox, give it the right network profile and credentials, start the harness, stream progress to whoever's watching, enforce time and cost budgets, collect the result, and clean everything up, even when something crashes halfway. That's a control plane: it doesn't do the work, it manages the things that do. Its core is a state machine per run and one rule: every exit path cleans up.

Control plane vs data plane

Air traffic control doesn't fly planes; it decides which plane goes where and when, keeps track of all of them, and reacts when one has a problem. The planes are the data plane. In this stack, the data plane is everything that executes a run (the harness, mcpbox, box, the gate). The control plane, runs, creates those pieces for each run, wires them together, watches them, and tears them down.

The split matters because the two have different jobs and different failure modes. The data plane runs untrusted work and may crash or be killed at any time. The control plane is trusted, keeps the records, and must survive its own restarts without losing track of anything.

What a run is made of

A run is a database record plus a set of resources that exist only while it's alive:

ResourceCreated byCleanup
Workspace directory (repo checkout)Control plane, before startDelete, after collecting outputs
cgroup and sandbox processesboxcgroup.kill, remove the cgroup
Gate profile and per-run socketControl plane tells the gateRemove the profile, delete the socket
CredentialsGate mints themRevoke
Harness processControl planeCancel, then kill if it doesn't stop
Trace file, event logHarness and control planeKeep: they're the record of what happened

The state machine

            ┌──────────── cancel ─────────────┐
            │                                  ▼
queued ─▶ preparing ─▶ running ⇄ waiting_for_approval
                         │
                         ├─▶ succeeded
                         ├─▶ failed       (error, crash, budget exceeded)
                         ├─▶ timed_out
                         └─▶ cancelled
                                  │
             every terminal state ┴─▶ cleanup() runs, exactly once in effect

Writing it down as an explicit state machine (a column in the database plus a function that allows only legal transitions) prevents a whole class of bugs: a run that's "succeeded" and "running" at once, a cancel that arrives during preparation and is lost, cleanup that runs twice and deletes the wrong thing.

A run's life, step by step

  1. A client submits a task. 
    POST /runs
{"task":"fix the failing test in parser", "repo":"me/parser", "profile":"go-dev",
 "budget":{"seconds":900, "usd":0.50, "steps":60}}
→ 201 {"id":"run_42", "status":"queued"}
  2. A worker picks it up when a slot is free (see concurrency) and moves it to preparing.
  3. Preparation: create the workspace (clone or restore from a snapshot), tell the gate to create the run's profile and socket and mint credentials, and choose the sandbox limits from the profile.
  4. Start: launch the harness for this run, configured to call mcpbox, which runs tools through box with this run's limits and gate socket. State becomes running.
  5. While running: the harness sends events (model output, tool calls, policy decisions) to the control plane, which stores them and streams them to watchers. It also sends heartbeats and usage so far.
  6. A policy "ask" pauses it: state waiting_for_approval, an approval event goes out, and the run resumes when POST /runs/run_42/approve arrives (or is denied when the approval times out).
  7. The harness finishes: the control plane records the outcome and any outputs (a branch name, a PR link, a report).
  8. Cleanup: kill whatever is left in the cgroup, revoke credentials, remove the gate profile, delete the workspace, keep the trace and events. The run reaches its terminal state.

the rest of the API

GET    /runs/run_42             status, timestamps, usage so far, exit reason
GET    /runs/run_42/events      live event stream (Server-Sent Events)
POST   /runs/run_42/approve     {"call_id":"call_9", "decision":"allow", "scope":"once"}
DELETE /runs/run_42             cancel

Streaming progress with Server-Sent Events

A watcher (a terminal UI, a web page, a phone notification service) wants to see the run as it happens. Server-Sent Events (SSE) is the simplest way: the client makes one ordinary HTTP request, and the server keeps the response open and writes events into it as plain text.

GET /runs/run_42/events
Accept: text/event-stream

id: 17
event: tool_call
data: {"call_id":"call_7","tool":"run_command","args":{"command":"go test ./..."}}

id: 18
event: tool_result
data: {"call_id":"call_7","exit_code":1,"duration_ms":4210}

id: 19
event: approval_needed
data: {"call_id":"call_9","tool":"git_push","args":{"branch":"agent/fix-parser"},"rule":"push-agent-branches-only"}

Each event is a few field: value lines followed by a blank line. Two properties make SSE a good fit:

  1. Resumable by design. Every event has an id. If the connection drops (a phone switching networks), the client reconnects and sends Last-Event-ID: 18.
  2. The server replays from there. Because events are stored in the database with increasing IDs, the server sends everything after 18 and then continues live. The watcher misses nothing.

Why not WebSockets? Progress only flows one way, server to client; SSE is plain HTTP that works through proxies, and actions in the other direction (approve, cancel) are ordinary POST requests. MCP's Streamable HTTP transport uses SSE for the same reasons (MCP page).

Budgets: who enforces what

A budget is only real if something enforces it, and different limits are best enforced at different layers:

BudgetEnforced byHow
Wall-clock time for the runControl planeA timer per run; on expiry, cancel (below), final state timed_out
Cost and tokensHarness, checked by control planeThe harness adds up usage after every model call and refuses the next call when over budget; the control plane cross-checks reported usage
StepsHarnessStop after N loop iterations
Time per tool callmcpbox / boxTimeout on each sandboxed command
Memory, CPU, processesbox (kernel)cgroup limits

The pattern: the closest layer enforces precisely, and an outer layer enforces a backstop. If the harness has a bug and keeps calling the model, the wall-clock timer still ends the run.

Cancelling a run

  1. DELETE /runs/run_42 marks the run cancelling in the database first, so the intent survives a crash.
  2. The control plane asks the harness to stop: in Go, cancelling the run's context.Context. A well-behaved harness stops after the current step and reports.
  3. A grace period (say 10 seconds) gives it time to finish cleanly.
  4. After the grace period, force: kill the harness process, and write 1 to the run's cgroup.kill so every sandboxed process dies at once.
  5. Normal cleanup runs (revoke, remove profile, delete workspace), and the state becomes cancelled.

Cleanup when things fail: reconciliation

The naive approach, "clean up at the end of the run function", fails exactly when it matters: if the control plane itself crashes or is killed, the end of the function never runs. You're left with orphans: sandboxes still running, tokens still valid, gate profiles still open.

The robust pattern, borrowed from Kubernetes controllers, is reconciliation: periodically compare what should exist (according to the database) with what does exist (on the machine), and fix the difference.

  1. The control plane is killed with kill -9 while three runs are active. No cleanup code runs.
  2. It restarts and, before accepting new work, runs a reconcile pass.
  3. It lists actual resources: cgroups under /sys/fs/cgroup/box/, workspace directories, gate profiles, unexpired tokens.
  4. It compares them with the database: those three runs are marked running, but their harness processes are gone and no heartbeat has arrived for a while.
  5. It marks them failed (reason: "control plane restarted") and runs their cleanup.
  6. It also removes anything with no matching run at all, for example a cgroup left by a run whose record was never written.
  7. The same pass runs every minute while the control plane is up, catching anything that leaks in normal operation.
Two properties that make this work
  • Idempotent cleanup: every cleanup step can safely run twice. Deleting a directory that's already gone, or revoking a token that's already revoked, is a success, not an error.
  • Heartbeats: the harness reports "still alive" every few seconds. A run with no heartbeat for, say, a minute is presumed dead. Without heartbeats you can't tell a slow run from a dead one.

Running many at once

  • A queue: new runs are rows with status queued. A worker claims the oldest one inside a database transaction, so two workers can never claim the same run.
  • A bounded worker pool: at most N runs at once, chosen to fit the machine's memory and CPU (the sum of the runs' cgroup limits is a good guide).
  • Backpressure: when the queue is too long, new submissions are refused (HTTP 429) rather than accepted and left waiting for hours.
  • No shared mutable state between runs: each has its own workspace, cgroup, socket and credentials. Runs don't coordinate; the control plane does.

Cold starts: why real platforms snapshot

Cloning a repo, installing dependencies and warming caches can take minutes, every run. Platforms avoid it by preparing an environment once and starting each run from a copy.

Layers with overlayfs

overlayfs combines read-only directories ("lower layers") with one writable directory ("upper") into a single merged view. Reads fall through to the layers below; writes go to the upper layer only. It's how container images work.

  1. Once: build a base layer (toolchain) and a deps layer (the repo with dependencies installed), both read-only.
  2. Per run: create an empty upper directory and mount the merged view: 
    mount -t overlay overlay \
  -o lowerdir=/layers/parser-deps:/layers/go-base,upperdir=/runs/42/upper,workdir=/runs/42/work \
  /runs/42/merged
    (The leftmost lower layer is on top: deps over base.)
  3. The sandbox uses /runs/42/merged as its workspace. Starting takes milliseconds, because nothing is copied.
  4. Every file the run changes lands in /runs/42/upper. That directory is the run's diff: useful for producing outputs.
  5. Cleanup unmounts and deletes the upper directory. The shared layers are untouched for the next run.

MicroVM snapshots

With microVMs (isolation page) you can go further: boot a VM, warm it up, then save its entire memory and device state to disk. Restoring that snapshot gives a running VM in a fraction of the boot time, with processes already started. One caveat worth knowing: every VM restored from the same snapshot starts with the same memory, including the state of random number generators and any IDs generated before the snapshot, so they must be refreshed after restore. Firecracker's documentation discusses this.

Storage: keep it boring

For one machine, SQLite is enough: a runs table (ID, status, timestamps, budget, usage, outcome), an events table (run ID, increasing event ID, type, JSON data) and an approvals table. It's a file, it's transactional, and it ships inside your binary. Move to something bigger only when a second machine forces you to.

What you'll build: runs

  • One binary: HTTP API, SQLite store, worker pool, reconcile loop.
  • The state machine as code, with a test for every legal and illegal transition.
  • SSE events with replay from Last-Event-ID; approvals; cancellation with a grace period.
  • Budgets: wall clock here; cost and steps reported by the harness and cross-checked.
  • Later: overlayfs layers for fast starts.
Done means
  • 20 runs in parallel; a third cancelled mid-way, a third timing out. Afterwards: zero leftover processes, cgroups, gate profiles or valid tokens.
  • Kill the control plane with kill -9 during that test, restart it, and the same is true after one reconcile pass.

Check yourself

Why isn't "clean up at the end of the run function" enough?

Because the function never reaches its end if the control plane crashes or is killed. Cleanup has to also happen from a reconcile pass that compares the database with what actually exists.

A watcher's connection drops for 30 seconds. How does it avoid missing events?

It reconnects with Last-Event-ID set to the last event it received, and the server replays stored events after that ID before continuing live.

Why does the control plane mark a run cancelling before doing anything else?

So the intent survives a crash. If the control plane dies mid-cancel, the reconcile pass sees cancelling and finishes the job.

What does overlayfs's upper directory contain after a run?

Exactly the files the run created or changed: the run's diff on top of the shared, read-only layers.
