Isolation: building a sandbox

How a process is shown a smaller world and given smaller budgets: namespaces, filesystems, cgroups, capabilities, seccomp and Landlock, the order they're applied in, and when you need gVisor or a microVM instead.

In one minute

Linux has no "container" object. A container is an ordinary process that the kernel shows a smaller world (namespaces: its own files, process list, network, users), gives smaller budgets (cgroups: memory, CPU, number of processes) and allows fewer actions (capabilities, seccomp, Landlock). You'll assemble those pieces by hand, in a specific order, which is the best way to understand what Docker, gVisor and microVMs each actually give you.

What a sandbox has to achieve

Run an untrusted command so that, whatever it does, it can only touch what you gave it:

  • Files: one working directory read-write, a few system directories read-only, nothing else visible.
  • Processes: it can't see or signal anything outside the sandbox.
  • Network: none at all, or only a path to the egress gate.
  • Resources: a memory cap, a CPU share, a process count limit and a wall-clock timeout.
  • Kernel surface: as few kernel features as possible, because every kernel feature is potential attack surface.
  • Cleanup: when it ends, nothing is left running.

Each mechanism below covers part of that list. None of them covers all of it, which is why you combine them.

Namespaces: a smaller world

A namespace gives a process its own copy of one kind of global resource. There are several kinds, each requested with a CLONE_NEW… flag when the process is created (or with unshare afterwards). The fastest way to understand them is the unshare command, which creates namespaces and runs a command inside them. All of these outputs were produced on a real Linux machine.

User namespace: "root" that isn't

$ id -u
1000
$ unshare --user --map-root-user sh -c 'id -u; cat /proc/self/uid_map'
0
         0       1000          1     # "uid 0 in here is uid 1000 outside, for 1 id"

Inside, the process has full root powers over things that belong to its namespace. Outside, any file it creates is owned by you and any access is checked as you. Creating a user namespace first is what makes all the others possible without sudo.

PID namespace: its own process list

$ sudo unshare --pid --fork --mount-proc sh -c 'ps -eo pid,comm'
    PID COMMAND
      1 sh
      2 ps

Two particularities. --fork is needed because a new PID namespace applies to the next process created, not the caller (the same quirk you saw on the processes page). And --mount-proc mounts a fresh /proc, because tools like ps read the process list from /proc; without it they'd still show the host's processes. A useful bonus: when PID 1 of a namespace exits, the kernel kills every other process in it, which gives you reliable cleanup for free.

Mount namespace: its own filesystem view

$ unshare --user --map-root-user --mount sh -c 'mount -t tmpfs none /mnt; touch /mnt/inside; ls /mnt'
inside
$ ls /mnt
                     # the host never saw that mount

The process gets a private copy of the list of mounted filesystems. Changes inside don't affect the host. On its own this doesn't hide anything (the copy starts identical to the host's); hiding comes from building a new root, below.

Network namespace: an empty network

$ unshare --user --map-root-user --net sh -c 'ip -brief addr; curl -sS https://example.com'
lo               DOWN
curl: (6) Could not resolve host: example.com

A new network namespace has only a loopback interface, and it's down. No routes, no DNS, no internet, no LAN, no cloud metadata service. Making it able to reach exactly one thing (the gate) is covered on the network page.

Building a private filesystem

A mount namespace starts as a copy of the host's view. To make the host's files unreachable, the sandbox builds a new, minimal tree and makes it the root:

  1. Make mounts private. By default, mount changes can propagate between namespaces. Marking everything private (mount --make-rprivate /, or the equivalent syscall) guarantees nothing you do leaks back to the host.
  2. Create an empty directory to become the new root, for example a fresh temporary directory per run.
  3. Bind-mount in what's needed. A bind mount makes an existing directory appear at a second location. Mount /usr, /lib and /bin read-only so programs exist; the run's workspace at /work read-write; a small tmpfs (memory-backed filesystem) at /tmp; a minimal /dev with only null, zero, random, urandom and tty.
  4. Switch root with pivot_root, then unmount the old root. Now /home, ~/.ssh and the rest of the host simply don't exist: no path leads there.
  5. Mount a fresh /proc for the new PID namespace.
Why not just chroot?

chroot changes where a process's / points, but the old root is still mounted, and a process with root powers can climb back out with a known trick. pivot_root swaps the root of the mount namespace, and unmounting the old root removes the escape route entirely. Container runtimes use pivot_root for this reason.

An alternative to the host's /usr is a separate root filesystem, for example an unpacked container image. That gives you a controlled, pinned set of tools per run (a Python image, a Go image) at the cost of managing images. A good decision to make consciously.

cgroups: smaller budgets

Control groups ("cgroups") put processes in a group and let the kernel account for and limit what the group uses. In cgroups v2 (the current version), the interface is just a directory tree of files under /sys/fs/cgroup. You limit a group by writing to its files and move a process into it by writing its PID.

step by step: stop a fork bomb (as root, in a VM)

  1. Create a group and limit it to 20 processes: 
    mkdir /sys/fs/cgroup/demo
echo 20 > /sys/fs/cgroup/demo/pids.max
  2. Move your current shell into it. Everything it starts from now on is in the group too. 
    echo $$ > /sys/fs/cgroup/demo/cgroup.procs
  3. Try to start 50 processes: 
    for i in $(seq 50); do sleep 60 & done
# after about 20: "fork: Resource temporarily unavailable"
  4. Ask the kernel what happened: 
    cat /sys/fs/cgroup/demo/pids.events
max 31            # 31 process creations were refused
  5. Kill everything in the group at once: echo 1 > /sys/fs/cgroup/demo/cgroup.kill. One write, no orphans. This is how box will clean up.
FileExampleEffect
memory.max512MAbove this, the kernel reclaims memory and then kills a process in the group ("OOM kill")
memory.eventsread itCounts, including oom_kill: how you tell "it crashed" from "we killed it"

Two practical notes. Controllers must be enabled for a group's children (+memory +pids +cpu in the parent's cgroup.subtree_control). And on systems run by systemd, an unprivileged user gets a delegated part of the tree, or you can run as root inside your VM while learning. In Go, SysProcAttr has UseCgroupFD/CgroupFD to start the child directly inside a group, so there's no moment where it runs unlimited.

Capabilities and no_new_privs

Root's powers are split into about forty capabilities. Inside a user namespace the sandboxed process holds all of them (relative to that namespace). Before exec, the sandbox drops every capability the command doesn't need, which is usually all of them.

The no_new_privs flag closes a different door: programs like sudo are "setuid", meaning they run with their owner's (root's) privileges whoever starts them. With no_new_privs set, exec can never gain privileges that way. It's one line, it's inherited, it can't be unset, and the kernel requires it before an unprivileged process may install a seccomp filter.

seccomp: fewer system calls

Everything a process does goes through system calls. seccomp lets a process install a small filter program that the kernel runs on every syscall it makes from then on. The filter looks at the syscall number (and optionally its arguments) and returns an action:

ActionEffect
allowThe call proceeds normally
errnoThe call fails with an error, such as "operation not permitted". The program sees a normal failure.
killThe process is killed immediately
logAllowed, but recorded: useful while developing a filter
user notificationThe call is paused and a supervisor process decides. This is how some sandboxes implement "ask" at the syscall level.

Which syscalls to refuse? Ones that ordinary programs never need and attackers love: mount, umount2, pivot_root (after setup), ptrace (inspecting other processes), bpf, perf_event_open, keyctl, kexec_load, unshare and setns (making or entering namespaces), init_module (loading kernel code). Docker's default profile refuses a few dozen of these.

Denylist or allowlist?

A denylist refuses known-dangerous calls and allows everything else: easy to get working, but new kernel versions add syscalls you didn't list. An allowlist permits only what you've seen programs need: much stronger, but you'll spend time finding out which calls npm or go build make (strace tells you). Starting with a denylist and moving towards an allowlist is a classic learning path.

The thread gotcha in Go

A seccomp filter applies to the thread that installs it. A Go program has several threads, so the filter must be installed with the "synchronize all threads" flag, or some threads stay unfiltered. Check that the library you pick does this.

Landlock: unprivileged file rules

Landlock lets a process restrict its own file access, without any privileges. It creates a ruleset ("this process may read under /usr, read and write under /work, nothing else"), applies it to itself, and from then on the kernel enforces it for the process and all its children. Newer kernel versions extend it, for example to restrict which TCP ports may be connected to.

If the mount setup already hides everything, why also Landlock? Defence in depth. Mount configuration is fiddly; a single wrong bind mount exposes a directory. Landlock is a second, independent check on the same thing. If one layer has a bug, the other still holds. Like seccomp, it applies per thread, so in Go you need a library that applies it to all threads.

Putting it together: the order matters

Here's the full sequence a sandbox runs, with the reason each step sits where it does. Steps 1–3 happen in the parent; the rest in the child, before it execs the command (see the re-exec trick).

  1. Create the cgroup and write its limits. Before the child exists, so it never runs unlimited.
  2. Start the child with new user, mount, PID, net, UTS, IPC and cgroup namespaces, directly inside the cgroup.
  3. Write the UID/GID maps for the child's user namespace (Go does this for you from SysProcAttr).
  4. Make mounts private. First thing in the child, before any mount, so nothing propagates.
  5. Build the new root with bind mounts: system dirs read-only, workspace read-write, tmpfs, minimal /dev.
  6. pivot_root and unmount the old root. The host filesystem is now unreachable.
  7. Mount /proc and set the hostname.
  8. Close every file descriptor except 0, 1 and 2. Inherited descriptors are open doors.
  9. Drop capabilities.
  10. Set no_new_privs. Required before the next two.
  11. Apply Landlock.
  12. Install seccomp, last. It would block mount, pivot_root and friends used above.
  13. Exec the command with a clean, explicit environment. Never pass through the parent's environment: it may contain secrets.
  14. Parent waits with a timeout. On timeout or completion, it writes 1 to cgroup.kill, removes the cgroup, deletes the run's temporary root, and reports the result.

The shared-kernel problem, and stronger options

Everything above is enforced by the same kernel the untrusted program is talking to. The kernel is huge, and bugs in it occasionally let a process break out of every namespace and filter at once. For code you mostly trust (your own agent working on your own repos), namespaces are a reasonable boundary. For code you don't (other people's tasks, a multi-tenant cloud product), you want a smaller boundary between the program and the real kernel.

gVisor: a kernel in user space

gVisor (written in Go) intercepts the sandboxed program's syscalls and handles them in its own user-space implementation of Linux, the "Sentry". The program believes it's talking to Linux; the real kernel only sees the Sentry, which itself runs with a tiny syscall allowlist. Cost: syscall-heavy workloads run slower, and a few Linux features behave differently. You use it as runsc, a drop-in container runtime.

MicroVMs: a real, tiny virtual machine

Firecracker (written in Rust, built for serverless platforms) uses the CPU's hardware virtualization (KVM on Linux) to run a separate guest kernel with a deliberately minimal set of virtual devices: a network card, a disk, a serial console, and a socket channel to the host ("vsock"). It boots to user space in roughly an eighth of a second and costs a few megabytes of memory overhead. An escape now requires breaking the hypervisor, a much smaller and better-defended surface than the full Linux syscall interface. Firecracker even runs itself inside namespaces, cgroups and seccomp (its "jailer"), so a hypervisor bug still lands in a sandbox.

Two related ideas you'll see mentioned: Kata Containers runs ordinary container images inside microVMs; WebAssembly runtimes run code compiled to Wasm with no access to anything unless explicitly granted. Wasm is great for tools you write yourself, but it can't run an arbitrary npm install, so it doesn't replace the options above for agents.

And on macOS?

None of the above exists on macOS. Its equivalent is Seatbelt: a process can be started under a policy profile (via sandbox-exec) that the kernel enforces for files, network and more. Several agent tools use it on Macs. For this project, develop on Linux and treat Seatbelt as one comparison blog post.

Check yourself

You set up a mount namespace but skip pivot_root. Can the sandboxed program read ~/.ssh?

Yes. A new mount namespace starts as a copy of the host's mounts, so everything is still visible. Hiding comes from building a new root and switching to it.

Why is seccomp installed last?

Because the filter typically blocks mount, pivot_root and other calls that the setup steps before it need. Install it earlier and your own setup fails.

Your process gets killed. How does box tell "out of memory" from "crashed"?

By reading the cgroup's memory.events file: if its oom_kill counter went up, the kernel killed it for exceeding memory.max.

When would you choose a microVM over namespaces?

When the code is genuinely untrusted (other people's tasks, a multi-tenant service), because namespaces share the host kernel and one kernel bug can break all of them. A microVM puts a hypervisor boundary in between.
