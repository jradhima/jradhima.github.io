Processes, syscalls and fork/exec

Every other page builds on this one. What a process is, why the kernel is the only place limits can really be enforced, and how a sandbox program starts a restricted process, with Python comparisons and a tiny Go program you can run.

In one minute

A running program can't touch anything (files, network, other programs) by itself. It has to ask the kernel, through system calls. That single doorway is why the kernel can enforce limits a program can't get around. A sandbox is a process the kernel has been told to restrict, and those restrictions survive exec, the call that swaps which program a process runs. So the recipe is: create a throwaway process, restrict it, then swap in the untrusted command. In Go you can't run your own code between "create" and "swap", so Go sandboxes start a second copy of themselves to do the restricting.

What a process is

When you run python script.py, the OS creates a process. It has two halves:

  • Memory: the program's code and its variables. This is what you think of as "the program".
  • Kernel-side settings: its process ID (PID), which user it runs as, its working directory, its environment variables, its open files, and, central to this guide, which parts of the system it can see (namespaces), its resource budget (cgroup) and which system calls it may make (seccomp).
An analogy for the rest of the guide

A process is a person in a building. Memory is what they know and are working on. The kernel settings are their badge: which rooms open, how much budget they have. exec replaces the person's knowledge and job but keeps the badge. A sandbox locks the badge down first, then swaps in the untrusted program, which starts life with the locked badge and can't take it off.

System calls: the only door

Your program runs in "user mode": the CPU won't let it touch the disk, the network card or another program's memory directly. To do anything outside its own memory it executes a system call ("syscall"), which hands control to the kernel along with a request: open this file, connect to this address, start this program. The kernel checks the request against the process's settings and either does it or returns an error. Linux has a few hundred syscalls; open, read, write, connect, clone and execve are the ones you'll meet constantly.

You can watch them with strace, which prints every syscall a program makes:

$ strace -f -e trace=execve,openat cat /etc/hostname
execve("/usr/bin/cat", ["cat", "/etc/hostname"], …) = 0     # start the cat program
openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3             # open the file; the kernel returns 3
myhost

Python's open(), Go's os.Open, a shell's cat: all of them end in the same openat syscall. That's the key point for sandboxing: every access to files, network or processes passes through this one narrow interface, so restricting it restricts everything, regardless of language or tool.

File descriptors: how processes talk

That = 3 above is a file descriptor: a small number the kernel gives a process to refer to an open thing. "Things" include files, but also network connections and pipes (one-way channels between processes). Every process starts with three:

0stdinsys.stdinKeyboard, or whatever is piped in
1stdoutsys.stdoutTerminal, or the next program in a pipe

In cat log.txt | grep error, the shell creates a pipe, connects cat's fd 1 to one end and grep's fd 0 to the other. Neither program knows; they just read and write their standard streams. Two consequences you'll see later: an MCP server over stdio is exactly this, with JSON messages on stdin/stdout (MCP page); and file descriptors are inherited by child processes, so a sandbox must close the ones the untrusted program shouldn't have.

Users, root, and why "root" can be fake

Every process runs as a numeric user ID (UID). Files have owners and permission bits, and the kernel compares the two on every access. UID 0, root, bypasses most checks. Historically root was all-or-nothing; modern Linux splits its powers into about forty capabilities (CAP_NET_ADMIN to configure networking, CAP_SYS_ADMIN for mounting and much more, and so on) that can be granted or dropped individually.

A user namespace adds a twist: a process can be UID 0 inside its namespace while the kernel maps it to your ordinary UID outside. Inside, it may do root-like things that only affect its own little world (mount filesystems there, change its own hostname). Outside, it's still just you. That's what lets you build a sandbox without sudo. The isolation page shows it in action.

Starting programs: fork, exec, wait

Unix creates processes in two steps that you can combine in different ways:

  • fork() clones the current process. Afterwards there are two nearly identical processes running the same program at the same line; the only difference is that fork returns 0 in the copy (the "child") and the child's PID in the original (the "parent").
  • exec() (properly execve) replaces the program running in the current process with another one. Same process, same PID, same kernel-side settings; brand-new code and memory.
  • wait() lets a parent sleep until a child exits and collect its exit code.

Under the hood, subprocess.run and cmd.Run() are fork + exec + wait: clone yourself, have the clone exec the command, wait for it. In Go, exec.Command("ls") on its own runs nothing; it only describes a process until you call Run() or Start().

see the difference in Python

# run: a NEW process runs echo; we wait; then we carry on
import subprocess
subprocess.run(["echo", "hello from echo"])
print("after")                  # prints: we are still here

# exec: THIS process turns into echo. There is no "after".
import os
print("before", flush=True)     # flush, because exec discards unwritten buffers
os.execv("/bin/echo", ["echo", "hello from echo"])
print("after")                  # never runs: the Python interpreter is gone

Restrictions belong to the process, and stick

Three properties make sandboxes possible:

  1. Restrictions are kernel-side settings, so they survive exec: the new program inherits them.
  2. Children inherit them too: everything the restricted program starts is restricted as well.
  3. They're one-way. A process can tighten its own limits but never loosen them. That's why the sandbox program (the "controller") doesn't restrict itself: it needs to keep working. It restricts a disposable process instead.

The unshare command shows all three. It creates a process with new namespaces, then execs your command in it:

$ unshare --user --map-root-user --uts sh -c 'hostname box; hostname; id -u'
box          # the hostname changed…
0            # …and we are "root", but only in this namespace
$ hostname
myhost       # outside: untouched
"Operation not permitted"?

Some distributions (recent Ubuntu, for example) block unprivileged user namespaces by default. In a VM you control, sudo sysctl kernel.apparmor_restrict_unprivileged_userns=0 allows them; or run the command with sudo and drop --user --map-root-user.

How a sandbox starts a process: the C way

The gap between fork and exec is where a sandbox does its work. The child is still running the sandbox's own code, so it can restrict itself and then exec the untrusted command:

  1. Fork. The sandbox (PID 100) forks; the child is PID 101, a copy running the same code.
  2. Parent waits. PID 100 calls waitpid(101) and sleeps.
  3. Child enters new namespaces (a user namespace first, so it's allowed to do the rest without real root), builds a private filesystem view and joins a cgroup with memory and process limits.
  4. Child applies the final filters: Landlock rules, then a seccomp syscall filter last, because that filter would block the mount calls of the previous step.
  5. Child execs the untrusted command. The sandbox's code is gone from PID 101; the command runs with every restriction inherited.
  6. Command exits, and the parent's waitpid returns its exit code.

Python has a hook for exactly that gap, subprocess.run(..., preexec_fn=setup), and its documentation warns it's unsafe in programs that use threads. That warning is the whole story of the next section.

Why Go can't, and the re-exec trick

Every Go program runs on several OS threads (for the garbage collector, the scheduler, your goroutines). fork() copies only the thread that called it, so a forked Go child would have a half-copied runtime, for example waiting forever on a lock held by a thread that no longer exists. So Go has no fork. Its os/exec does fork and exec in one controlled step, with only a fixed list of options (SysProcAttr) in between. You can't add your own code there.

The fix: make "the code in between" a separate run of the same binary. The sandbox starts /proc/self/exe (a link the kernel provides to the running program's own file) with a marker argument, and asks for the new namespaces at creation time. That second run is a brand-new process with a fresh Go runtime, already inside the namespaces. It sees the marker, does the setup, and execs the real command.

jail.go: a complete toy. Three namespaces only, but the real structure.

package main

import ("fmt"; "os"; "os/exec"; "syscall")

func main() {
    if len(os.Args) > 1 && os.Args[1] == "__init" {   // am I the second run?
        child(os.Args[2:])
        return
    }
    parent(os.Args[1:])                                // no marker: first run
}

func parent(args []string) {
    fmt.Println("parent: pid", os.Getpid())
    // describe a process: "run MYSELF again, with __init in front of the real command"
    cmd := exec.Command("/proc/self/exe", append([]string{"__init"}, args...)...)
    cmd.Stdin, cmd.Stdout, cmd.Stderr = os.Stdin, os.Stdout, os.Stderr
    cmd.SysProcAttr = &syscall.SysProcAttr{
        // "create it inside NEW user, hostname and PID namespaces"
        Cloneflags:  syscall.CLONE_NEWUSER | syscall.CLONE_NEWUTS | syscall.CLONE_NEWPID,
        UidMappings: []syscall.SysProcIDMap{{ContainerID: 0, HostID: os.Getuid(), Size: 1}},
        GidMappings: []syscall.SysProcIDMap{{ContainerID: 0, HostID: os.Getgid(), Size: 1}},
    }
    if err := cmd.Run(); err != nil {                  // start it and WAIT
        fmt.Fprintln(os.Stderr, "run failed:", err)
        os.Exit(1)
    }
}

func child(args []string) {
    fmt.Println("child: pid", os.Getpid())             // 1: first process in its PID namespace
    must(syscall.Sethostname([]byte("box")))           // "restrict" (real: mounts, Landlock, seccomp)
    path, err := exec.LookPath(args[0])
    must(err)
    must(syscall.Exec(path, args, []string{"PATH=/usr/bin:/bin"}))   // become the command
}

func must(err error) {                                 // our helper, not a Go built-in
    if err != nil { fmt.Fprintln(os.Stderr, "fatal:", err); os.Exit(1) }
}
$ go mod init jailtoy && go build -o jail .
$ ./jail sh -c 'echo "sh: pid=$$ host=$(hostname)"'
parent: pid 936
child: pid 1
sh: pid=1 host=box

The parent's memory is not copied to the child: it's a fresh process started from the same file. That's why the threads problem disappears.

Questions people usually have at this point

  • So the command runs twice? No. Our program runs twice (parent path, then child path). Your command runs once, at the end, when the child replaces itself with it.
  • Is __init special? No, any marker works. But the child path must fail closed if someone runs it directly: in the toy, ./jail __init sh outside namespaces fails at Sethostname and exits instead of running sh unrestricted. Real code adds an explicit check (for example that its PID is 1) or uses a marker users can't set by accident.
  • What does must() do? It's a five-line helper: on error, exit. Go functions return errors and it's legal to ignore them; must makes that impossible. For a sandbox it's essential: a failed setup step must never be followed by running the command anyway.
  • How would the child get its configuration? It starts with empty memory, so configuration has to be passed in: arguments, environment variables, or JSON over an extra pipe (cmd.ExtraFiles, which appears in the child as fd 3). Container runtimes like runc pass their config this way.
  • Why not pass the namespace flags straight to the real command? You'd get namespaces, but nowhere to run the mount, Landlock and seccomp setup, which must happen inside the new process before the command starts.

Check yourself

Why can the kernel enforce limits that a program can't get around?

Because a program can't touch files, network or other processes without a system call, and every system call goes through the kernel, which checks it against the process's settings. There's no side door in user mode.

After syscall.Exec succeeds, what runs the next line of your Go code?

Nothing. The process's code and memory were replaced by the new program. Exec only returns if it failed.

Why doesn't the sandbox program restrict itself instead of a child?

Restrictions can't be undone. The controller needs to keep creating runs, reading results and cleaning up, so it restricts a disposable process instead.

A forked child inherits open file descriptors. Why does that matter for a sandbox?

An inherited descriptor is an open door that bypasses the filesystem view: a file, socket or pipe the parent had open stays usable in the child. The sandbox must close (or mark close-on-exec) everything except stdin, stdout and stderr before exec.
