Part 10 · Doing it

Build plan

The order to build things in, what "done" means for each part, the decisions that are yours to make, how to lay out the repo, and what to read along the way.

In one minute

Build in an order where every stage is usable on its own and the next one builds on it: MCP server first (useful from day one, in any agent), then the sandbox under it, then tracing to see everything, then egress and credentials, then policy, and finally the harness and control plane that assemble it all. Tests from the first commit, a short write-up after each component, and every design decision written down before you build.

Why this order
  • MCP first because it's small, it's immediately useful from tools you already use, and it gives every later component a way to be exercised.
  • Sandbox second because it's the deepest topic and everything below the harness depends on it.
  • Tracing before the rest because from then on you can see what your components actually do, which makes debugging egress and policy far easier.
  • Harness and control plane last because by then they're assembly of parts you already understand, not a tutorial you're following.

Decisions that are yours

None of these has a single right answer. Before building each component, write a short decision note (a few lines in docs/decisions/: the choice, the alternatives, why). Revisiting them later is where much of the learning happens.

ComponentOpen questions
mcpboxIs run_command enough, or do file tools earn their place? How is output truncated, and what does the model see when it is? One server process per run, or one for many?
boxHost /usr read-only, or separate images per profile? Seccomp denylist or allowlist? What happens to a run's files when it ends? How does the child receive its configuration?
traceWhat counts as a span? Full content, or hashes and sizes by default? Where is the redaction list maintained?
gateHostname-only, or TLS termination too? Allowlist per run, per profile or per task type? If the gate crashes, do runs fail closed (they should; how do you test it)?
credentialsFine-grained tokens or a GitHub App? How short-lived is short enough? What happens to a run when minting fails?
policyWhat makes content untrusted: the source, the repo owner, the tool? Can a human clear taint? Rules in YAML or in Go? Which tools are structured, and which stay as raw shell?
runsSQLite or plain files? How do approvals reach you when you're away from the terminal? What's the heartbeat interval and the "presumed dead" threshold?
loopWhich model provider first? When do old tool results get shrunk? What exactly counts as "stuck"? Add code mode, and if so, in which language and which sandbox?

Working rules

  • Tests from the first commit. For box they're escape attempts; for policy, table-driven cases; for mcp, a fake client over pipes; for runs, kill-and-reconcile tests.
  • Every component works on its own through a boring interface (CLI, JSON over stdio, HTTP, MCP, OTLP). If testing one component requires running another, the interface is wrong.
  • Standard library first. Add a dependency when it clearly earns its place: x/sys, a Landlock library, a seccomp library, the OTel SDK, the MCP Go SDK (after your own version), a SQLite driver, one model SDK.
  • Fail closed everywhere. If setup, the gate, minting or policy fails, the run stops. It never continues with fewer protections.
  • Each package has a one-paragraph README: what problem it solves, its interface, what it deliberately doesn't do.
  • Write it up when a component is done. The write-up is how you check that you understand it, and it's what other people will see.

Reading list, by topic

TopicRead
ProcessesMan pages (on Linux or at man7.org): fork(2), execve(2), clone(2), unshare(1). The Go standard library's os/exec and syscall source, especially forkAndExecInChild.
MCPThe specification at modelcontextprotocol.io: lifecycle, tools, transports, and the security best practices page. The JSON-RPC 2.0 specification (short). The official Go SDK.
Isolationnamespaces(7), user_namespaces(7), cgroups(7), seccomp(2), landlock(7). The kernel's cgroup v2 documentation. Liz Rice's "Containers from scratch" talk (in Go) and her book Container Security. runc's source.
Stronger isolationThe Firecracker paper (NSDI 2020). gVisor's architecture documentation. LWN.net articles on seccomp and Landlock.
NetworkThe HTTP specification's section on CONNECT (RFC 9110). Any good introduction to TLS certificates and trust stores. OWASP's material on SSRF.
IdentityYour cloud provider's workload identity federation docs (read how the token exchange actually works). GitHub's docs on GitHub App installation access tokens. An introduction to JWTs.
PolicySimon Willison's writing on prompt injection, the dual-LLM pattern and "the lethal trifecta". Defeating Prompt Injections by Design (CaMeL, Google DeepMind, 2025). The OWASP Top 10 for LLM applications.
Harness & code modeCloudflare's "Code Mode: the better way to use MCP" post. Anthropic's engineering post "Code execution with MCP", on progressive disclosure, filtering data in code, and the sandboxing it requires.
TracingOpenTelemetry's concepts pages (traces, context propagation). The OTel GenAI semantic conventions. The W3C Trace Context specification.
Control planeThe Server-Sent Events section of the HTML standard. Kubernetes' explanation of controllers and reconciliation. The overlayfs documentation in the kernel docs. Firecracker's snapshotting docs.

Glossary

Audit logAppend-only record of every decision; hash-chained to make tampering detectable
Bearer tokenA credential that works for whoever holds it
Bind mountMaking an existing directory appear at a second location
CapabilityOne slice of root's powers, granted or dropped individually
cgroupA kernel group of processes with resource accounting and limits
CONNECTThe HTTP method that asks a proxy for a tunnel to a host and port
Code modeThe harness presents tools as functions; the model writes a program that calls them, run in a sandbox
Control planeThe system that creates, tracks and cleans up runs, as opposed to the parts that do the work
DNS rebindingMaking a hostname resolve to a different address between a check and a connection
EgressOutbound network traffic
execReplacing the program running in a process; the process and its restrictions stay
File descriptorA small number a process uses to refer to an open file, socket or pipe
forkCloning the current process
gVisorA user-space implementation of Linux that intercepts a sandboxed program's syscalls
HarnessThe program that runs the agent loop and executes tool calls
JSON-RPCA small convention for remote function calls in JSON; MCP is built on it
JWTA signed JSON document making claims like "I am X, valid until T, for Y"
LandlockLets an unprivileged process permanently restrict its own file (and some network) access
MCPModel Context Protocol: a standard for offering tools to any agent harness
Metadata serviceThe cloud VM's local endpoint (169.254.169.254) that hands out the VM's credentials
MicroVMA minimal virtual machine with its own kernel, booting in a fraction of a second
NamespaceA kernel feature giving a process its own view of one kind of resource
no_new_privsA process flag that prevents gaining privileges through exec
overlayfsA filesystem that stacks read-only layers under one writable layer
pivot_rootSwapping a mount namespace's root filesystem, so the old one can be removed
Prompt injectionInstructions hidden in content the agent reads, which the model may follow
ReconciliationRepeatedly comparing what should exist with what does, and fixing the difference
seccompA kernel filter on which system calls a process may make
SNIThe hostname a client sends unencrypted at the start of a TLS connection
Span / traceA span is one timed operation; a trace is the tree of spans for one run
SSEServer-Sent Events: a long-lived HTTP response carrying a stream of text events
SyscallA request from a program to the kernel; the only way to touch anything outside the program
TaintA label meaning "this session has seen untrusted content"
TLS terminationDecrypting traffic at a proxy, using a CA the client trusts
traceparentThe standard string carrying trace context between processes
Workload identityA platform vouches for a running job, which exchanges that proof for a short-lived credential
