Tracing agent runs

How to know what an agent did, in what order, why it took so long and what it cost, across several processes, without leaking secrets into your logs.

In one minute

An agent run is dozens of model calls and tool calls across several processes, sometimes over hours. When it does something wrong, slow or expensive, you need the story: what it saw, what it decided, in what order, how long each step took and what it cost. A trace is that story as a tree of timed operations ("spans"). The interesting engineering is keeping one tree across process boundaries, deciding what to record, and making sure secrets never end up in it.

Logs, metrics, traces

What it isAnswersExample
LogsTimestamped lines of text or JSON"What happened at 14:02?"tool run_command exit=1
MetricsNumbers aggregated over time"How many runs failed today? What's the average cost?"runs_failed_total 12
TracesTrees of timed, nested operations"Why did this run take 12 minutes, and what led to that action?"The tree below

For agents, traces are the most useful of the three, because the questions are about one specific run's sequence of decisions. Metrics can be derived from traces later.

run "fix failing test"                            12.4s   $0.031
├─ chat  (in 4.1k / out 220 tokens)                1.9s
├─ policy.decide run_command → allow               0.1ms
├─ execute_tool run_command "go test ./..."        4.2s    exit=1
│  └─ box.run                                      4.1s    peak 178 MB
├─ chat  (in 5.3k / out 410 tokens)                2.3s
├─ execute_tool write_file parser.go               10ms
└─ execute_tool run_command "go test ./..."        3.8s    exit=0

Anatomy of a span

{
  "trace_id":  "4bf92f3577b34da6a3ce929d0e0e4736",   // shared by every span in this run
  "span_id":   "00f067aa0ba902b7",                   // this operation
  "parent_id": "a3ce929d0e0e4736",                   // the operation it happened inside
  "name":      "execute_tool run_command",
  "start":     "2026-11-03T09:30:02.114Z",
  "end":       "2026-11-03T09:30:06.320Z",
  "status":    "error",
  "attributes": {
    "gen_ai.operation.name": "execute_tool",
    "gen_ai.tool.name":      "run_command",
    "gen_ai.tool.call.id":   "call_7",
    "box.exit_code":         1,
    "box.peak_memory_bytes": 187236352
  },
  "events": [{"time": "…", "name": "output_truncated", "attributes": {"original_bytes": 5242880}}]
}

The tree is built purely from parent_id links: any span whose parent is another span's ID is drawn under it. Attributes are key-value facts. Events are timestamped moments inside a span.

How a trace gets built, step by step

  1. The run starts. The harness creates a root span named run, with a fresh random trace ID and no parent.
  2. The harness calls the model. It starts a chat span whose parent is the root span, records the model name, and when the response arrives adds the token counts and ends the span.
  3. The model asks for a tool. The harness starts an execute_tool span (parent: root), with a child span for the policy decision.
  4. The tool runs in another process. The harness passes the trace context along (next section), so mcpbox and box can create spans whose parent is the execute_tool span, even though they're separate programs.
  5. Each span is ended and exported as it finishes: written to a file, or sent to a tracing backend. The viewer reassembles the tree from the IDs.

Inside one Go process, the "current span" travels in a context.Context. Starting a span returns a new context; anything started with that context becomes its child automatically:

ctx, span := tracer.Start(ctx, "execute_tool "+call.Name, trace.WithAttributes(
    attribute.String("gen_ai.operation.name", "execute_tool"),
    attribute.String("gen_ai.tool.name", call.Name),
    attribute.String("gen_ai.tool.call.id", call.ID),
))
defer span.End()
res, err := runner.Run(ctx, spec)    // spans started inside Run nest under this one

Crossing process boundaries

A context.Context doesn't cross into another process. The trace context has to be written into whatever goes between them. The standard format is the W3C traceparent string:

00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
│  │                                │                └ flags (01 = sampled: record it)
│  │                                └ parent span ID (the span on the sending side)
│  └ trace ID
└ version

Each hop needs a carrier, and in this stack each hop is different:

  1. Harness → mcpbox (MCP): MCP requests have a _meta field for extra data. Put "traceparent": "00-…" there in each tools/call. Your server reads it and starts its spans as children. (This is a convention you choose; check whether a standard has emerged by the time you build it.)
  2. mcpbox → box: pass it as an environment variable, TRACEPARENT, to the box process (if box is a separate CLI) or just pass the ctx (if mcpbox imports box as a package).
  3. Sandboxed program → gate: the interesting one. For HTTPS without decryption, the gate can't see any header inside the tunnel. But it knows which run a connection belongs to, from the socket the connection arrived on (Design B). So the gate records spans tagged with the run's ID and the box span's ID it was given when the run was set up. The tree stays connected through run identity rather than through headers.
Why this is worth doing properly

Without propagation you get three disconnected stories: the harness thinks the tool took 4 seconds, box knows the process used 178 MB, and the gate knows it refused a connection. With it, you see that the tool call was slow because npm install kept retrying a host the gate refused. Getting this right end to end teaches you how distributed tracing works in any system.

OpenTelemetry, briefly

OpenTelemetry (OTel) is the vendor-neutral standard for producing traces (and metrics and logs). The pieces:

  • API: what your code calls (tracer.Start, span.End).
  • SDK: the implementation that collects spans, batches them and hands them to an exporter.
  • Exporter: where spans go: a file, standard output, or a backend over OTLP, OTel's wire protocol.
  • Backend: stores and displays traces. For local learning, Jaeger runs as a single container with a web UI and accepts OTLP, which gives you a free trace viewer.

OTel also defines semantic conventions: agreed attribute names so different tools understand each other. The GenAI conventions cover model and tool calls, for example gen_ai.operation.name (chat, execute_tool), gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens and gen_ai.tool.name. They're still evolving, so treat them as a starting vocabulary and check the current version.

What to record, and what never to record

AlwaysOpt-in (useful but big or sensitive)Never
IDs, timings, statusFull prompts and model responsesCredentials, in any form
Model name, token counts, costFull tool argumentsContents of files you know are secret (.env, keys)
Tool name, exit code, durationFull tool outputs
Sizes and hashes of arguments and outputs
Policy decisions, egress decisions

Recording a hash and size instead of the content is a useful middle ground: you can't read the content from the trace, but you can tell whether two runs saw the same input, and look the content up elsewhere if you kept it.

Redaction happens before writing

Once a secret is written to a trace file or sent to a backend, it's too late: it's in backups, indexes, caches. So redaction runs inside the process, before export:

  1. Known formats: many tokens have recognizable shapes (GitHub tokens start with ghp_ or github_pat_, AWS access keys with AKIA, private keys contain -----BEGIN). Replace matches with [REDACTED:github-token].
  2. Known values: if a component knows the exact secrets in play, it can replace exact matches. (With credential injection, the sandbox side ideally holds none.)
  3. Truncate large payloads to a fixed size and record the original size.
  4. Test it: a test that plants a fake token in a tool output and asserts it never appears in the exported trace.

Cost: just arithmetic, but do it per run

Model APIs report token counts in each response: input tokens, output tokens, and often cached input tokens, which are cheaper. Multiply by the price for that model and record the result on each chat span, then sum it on the root span. Per-run cost, broken down by step, is the number that tells you a run spent 80% of its budget re-reading a huge file every turn, which is a harness fix (context management).

Replay: re-running a run without paying for it

If the trace records the full model responses (opt-in content), you can replay a run deterministically:

  1. Record: during a real run, each model response is saved with its step number and a hash of the request that produced it.
  2. Replay: run the harness in replay mode. Instead of calling the model API, it returns the recorded response for each step.
  3. Tools run for real (or are replayed from recorded outputs too, if you want full determinism).
  4. Detect divergence: if the harness builds a different request than the one recorded (because you changed something), the hashes don't match, and replay stops and tells you where.

That turns any interesting run into a free, repeatable test case for the harness itself.

From traces to evals

A trace is also the input for checking behaviour. Instead of only asking "did the final answer look right?", you can assert things about the trajectory:

  • Tests were run after the last file edit and before the run finished.
  • No git_push happened without an approval.
  • The run never needed more than three attempts at the same command.
  • The final workspace state matches the expected one.

A set of small tasks with assertions like these, run after each change to the harness or a component, is how you know you didn't make things worse.

What you'll build: trace

  • A small Go package around the OTel SDK: start and end spans with the GenAI attribute names, plus your own box.*, gate.* and policy.* attributes.
  • Exporters: JSON lines to a file per run (default), and OTLP so you can view runs in Jaeger.
  • Propagation: traceparent in MCP _meta, in the environment for box, and by run identity at the gate.
  • A redaction step before export, with a test that plants a fake token.
  • trace view run.jsonl: a terminal tree viewer with durations, tokens and cost.
  • Later: trace replay run.jsonl.
Done means
  • One run produces one connected tree spanning the harness, mcpbox, box and gate, and a planted secret never appears in it.

Check yourself

How does a viewer know which span goes under which?

From the IDs alone: every span records its parent's span ID, and all spans in a run share the trace ID. The tree is reassembled from those links.

Why can't the gate read a traceparent header on HTTPS traffic, and how does it stay in the tree anyway?

Without TLS termination the headers are encrypted inside the tunnel. The gate identifies the run from the connection itself (the per-run socket) and attaches its spans using the run's ID and the span context it was given at run setup.

Why redact inside the process instead of in the tracing backend?

Because once a secret has been written or sent, copies exist in places you don't control (files, backups, indexes). Redaction has to happen before anything leaves the process.

What does recording a hash of a tool output give you that recording nothing doesn't?

You can tell whether two runs saw identical output, and detect when the same input led to different behaviour, without storing the content itself.
