agentbox: agents that never see your credentials

A coding agent that runs gcloud and glab on your behalf is useful, and a liability: anything that can run env can read your tokens. This experiment keeps bash and the internet, but takes the real credentials out of the agent's reach.

TL;DR

The agent runs in a container that only sees fake placeholder tokens, on a network with no route out. Its only exit is a small proxy that swaps in the real GitLab, GitHub, GCP or Anthropic token, and only for the hosts that token belongs to. CLIs work unchanged. GCP only ever gets 1-hour access tokens. It was tested on Docker, Podman and gVisor on x86_64 Linux. The whole thing is about 450 lines.

The problem

At work we use GCP workstations with our own credentials (gcloud auth login, ADC) and a long-lived GitLab token. Giving an agent skills to drive those CLIs is very productive. But the agent is unsandboxed, so a malicious skill or a prompt injection can simply read the tokens:

GitLab token

Long-lived. Whoever has it can push code or rewrite CI pipelines to exfiltrate secrets.

gcloud refresh token

Access tokens last an hour, but ~/.config/gcloud holds a refresh token that lasts until revoked.

Metadata server

On a GCP VM, 169.254.169.254 hands any process the machine's service-account token.

Blocking everything

Taking away bash or the internet makes the agent useless. That's not an option.

So the goal is narrow and concrete: the agent can use the credentials, but can't take them.

The design

Two containers per session. The agent sits inside a network perimeter with no route out. The proxy straddles that perimeter: it is the only door, and the only place real tokens exist.

# ~/.config/agentbox/proxy.yaml: the whole configuration
allow_hosts: ["*"]                 # keep the internet open
secrets:
  GITLAB_TOKEN:
    hosts: ["gitlab.example.com"]
    file: gitlab-token
    git: true                      # git push/pull over HTTPS just works
  GCP_TOKEN:
    hosts: ["*.googleapis.com"]
    gcp_adc: true                  # 1-hour tokens, refreshed by the proxy

Starting a session is one command in your repo: agentbox pi, agentbox claude or agentbox bash. Both containers are created fresh and deleted on exit.

Hiding, then replacing

Two layers, and it matters which does what. The first does most of the work. The second only touches strings the proxy made up itself.

1 · Hiding

Real secrets are never put in the container. It gets your repo, a read-only folder of placeholders and the proxy's certificate, and nothing else: no home directory, no host env vars, no ~/.config/gcloud, no Docker socket.

2 · Replacing

The proxy looks for its own random placeholder strings in outgoing headers and swaps them for the real value, for allowed hosts only. It never scans for real tokens.

Hiding is only as good as what you mount

A .env with real keys inside your repo is visible to the agent, and the proxy does nothing about it.

The variable name doesn't matter, the value does. GITLAB_TOKEN is just the name the placeholder is exported under. If a tool wants GL_TOKEN or its own config file, put the same placeholder there (export GL_TOKEN=$GITLAB_TOKEN). It still travels in a header and still gets swapped.

SwappableNot swappable
Bearer tokens, PRIVATE-TOKEN, git's Basic auth: anything sent as-is in a headerSecrets the client computes with: service-account JSON keys, AWS SigV4, mTLS certs, SSH keys. A placeholder can't produce a valid signature, so use token-based auth (ADC, HTTPS git)
Tokens read from env vars, config files or token files: they all end up in a headerTokens in a body or URL (?private_token=), and non-HTTP protocols

Using it day to day

  1. Once: agentbox init creates two files in ~/.config/agentbox/: proxy.yaml (hosts and secrets) and agentbox.env (what goes in the image).
  2. Tokens become files. The proxy reads each real value from a file in that folder (or mints GCP tokens from your ADC). It can't see your shell's env vars, so a token exported in ~/.bashrc has to be copied into a file. Then point ~/.bashrc at the file, so there's one copy.
  3. Choose the image. The default is lean: base tools plus pi. List more agents and packages in agentbox.env and run agentbox build.
  4. Every day: cd into a repo and run agentbox pi, agentbox claude or agentbox bash.
# ~/.config/agentbox/agentbox.env
AGENTBOX_NPM_PACKAGES="@mariozechner/pi-coding-agent@0.73.1 @anthropic-ai/claude-code@2.1.318"
AGENTBOX_APT_PACKAGES="postgresql-client"
AGENTBOX_GCLOUD=1
AGENTBOX_MOUNTS="~/.pi/agent/skills:~/.pi/agent/skills"     # read-only
AGENTBOX_ENV="CLOUDSDK_CORE_PROJECT=my-project"
Your home directory doesn't come along

Not your ~/.bashrc, not your skills, not your host's tools. That's deliberate, because dotfiles are where tokens hide. You opt in:

You want in the boxHow
Your agent's skills or promptsMount them read-only with AGENTBOX_MOUNTS. Never mount a file that holds a key
Aliases and shell setupA small secret-free box.bashrc, mounted as ~/.bashrc, plus BASH_ENV so the agent's non-interactive shells read it too
Plain settings (default project, GitLab host)AGENTBOX_ENV
Tools like gcloud or psqlAdd them to the image in agentbox.env
Existing git@host: clonesNothing: SSH remotes are rewritten to HTTPS for hosts marked git: true

Why it looks like this

DecisionWhy
Inject at a proxy, not MCP servers per toolOne mechanism covers every CLI and every agent's own API calls, with no tool code to maintain. An MCP server that can run any gcloud command protects no better against theft.
Containers, with gVisor optionalMature, already on workstations, no nested virtualization. The threat is a tricked agent reading files, not a kernel exploit. gVisor is one flag away if that changes.
Two containers and a network with no route outHTTPS_PROXY alone is a suggestion: curl --noproxy '*' ignores it. A separate network makes the proxy the only door, and cuts off the metadata server.
Swap in headers onlyThat's where tokens travel. Swapping in bodies would let the agent write the real token into an issue or gist.
Re-mask responsesAn allowed host that echoes headers (debug endpoints) would otherwise hand the real token back.
Proxy blocks private IPsThe proxy itself can reach the metadata server. Without this check, the agent could ask the proxy to fetch the workstation's token.
GCP through ADC → 1-hour tokensThe refresh token never enters the box. gcloud and bq read the placeholder from CLOUDSDK_AUTH_ACCESS_TOKEN_FILE.
Secrets come from files, not env varsThe proxy lives in its own container. A chmod 600 file is simpler than piping real values through Docker on every run.
A lean image you configurePreinstalling every agent made a big image full of unused tools. One agentbox.env file lists what you want.
Everything fresh per sessionNew network, CA and placeholders every run. The CA's private key never leaves the proxy.

How it was tested

An end-to-end script starts a real session with a throwaway config, runs checks inside the box, then scans everything the agent saw or received for the real secret. Development happened on an arm64 Mac, but the real runs were on an x86_64 Ubuntu VM to match a GCP workstation.

On top of that, on Docker:

  • GitHub: a real token was injected. The API call and a private git clone worked.
  • GCP and Anthropic: gcloud, bq and Claude Code (Haiku) got fake tokens, and Google and Anthropic answered "invalid credentials". That proves the full path (proxy, TLS trust, client honoring the proxy) without touching a real account.

Limits and cheap wins

It stops theft, not misuse

A hijacked agent can still do anything the token allows during the session, and with the internet open it can still send data out. Plain containers also share the host kernel. Those are handled by permissions and by gVisor, not by the proxy.

Protect main

On important repos the agent opens MRs; on solo repos let it push.

Protected CI variables

Feature-branch pipelines never get deploy secrets, even if the agent edits CI.

Read-only GCP identity

Impersonate a read-only service account for the agent, and do writes yourself.

Tighten allow_hosts

The proxy log shows which hosts are used. It's the only control on exfiltration.
